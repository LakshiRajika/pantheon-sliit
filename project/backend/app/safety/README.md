# Safety

This directory implements the guardrails applied around every LLM call: validating raw input before it's processed, redacting PII before anything reaches a model, screening for prompt-injection attempts, fencing untrusted content, validating structured LLM output against schemas, scrubbing unsafe text on the way out, and a declarative policy for what's blocked outright or requires human sign-off. The pieces are composed together in `safety_pipeline.py`, which is what the rest of the app (chat handlers, agents) actually calls.

## Files

- **`input_validation.py`** — `validate_chat_input(text)` rejects empty/whitespace-only messages, messages over `MAX_CHAT_MESSAGE_CHARS` (4000), and null bytes, returning the trimmed text otherwise. `validate_upload(filename, mime_type, size_bytes, max_mb)` rejects uploads with a disallowed MIME type (only PDF/PNG/JPEG allowed), files over the configured size limit, or filenames containing path separators. Both raise `ValidationFailedError` from `app.core.exceptions`.

- **`pii_detector.py`** — `detect_pii(text)` scans text against a dict of regex `PATTERNS` for email, phone, passport, and Sri Lankan NIC numbers, returning a list of findings (label, position, matched value) for every hit. A comment flags this as an MVP regex-based detector that should be replaced with a proper NER/Presidio-based detector before production use, since regexes will under- and over-match.

- **`pii_redactor.py`** — `redact(text)` calls `detect_pii` and replaces every match with a stable pseudonym like `EMAIL_0001`, built by `_pseudonym_for`. Pseudonyms are tracked in module-level, in-memory, process-local dicts (`_PSEUDONYM_COUNTERS`, `_PSEUDONYM_MAP`); replacements happen from the end of the string backward so earlier offsets stay valid. A comment notes a real deployment would keep this mapping in protected backend storage rather than in-memory, so original values stay recoverable by authorized workflows but are never sent to the LLM.

- **`prompt_injection.py`** — `screen_for_injection(text)` checks text against a list of regex `_INJECTION_MARKERS` (phrases like "ignore previous instructions", "you are now", "reveal your prompt", "act as an admin") and returns the patterns that matched. `wrap_as_untrusted(text, source)` fences a block of text in `<untrusted_{source}>...</untrusted_{source}>` tags with an instruction telling the model to treat it as data, not instructions. A comment is explicit that this is a coarse heuristic screen, not a guarantee — the real control is that the LLM is never granted permissions directly, and every tool re-checks authorization independently of anything the model says.

- **`policy.py`** — Declarative safety policy, separate from the validators. `SafetyAction` is a `StrEnum` of possible decisions (`ALLOW`, `REDACT_AND_ALLOW`, `BLOCK`, `ESCALATE`). `BLOCKED_TOPICS` is a list of fully disallowed requests (e.g. "generate fake customs certificate", "bypass inspection", "falsify bill of lading"), checked case-insensitively by `is_blocked_topic(text)`. `CONSEQUENTIAL_ACTIONS` is a set of action names (`approve_clearance`, `override_risk_flag`, `release_shipment`) that an assistant/agent may recommend but never finalize unsupervised, checked by `is_consequential_action(action_name)`. The intent is to keep business rules here declaratively rather than scattering ad hoc `if` checks through agents and chat handlers.

- **`output_validator.py`** — `validate_structured_output(raw, schema)` parses a raw dict through a given Pydantic `BaseModel` schema, raising `ValidationFailedError` on failure; every LLM structured output is meant to go through this before being trusted anywhere downstream (persistence, UI, another agent). `strip_unsafe_text(text)` is a last-mile guard that checks for danger markers (a stack trace header, or API-key prefixes like `sk-`, `gsk_`, `AIza`) and replaces the entire response with a generic failure message if any are found, so a leaked secret or trace never reaches the user.

- **`safety_pipeline.py`** — Composes the above into three entry points used by callers elsewhere in the app. `sanitize_user_input(text)` runs chat input through `validate_chat_input`, then `screen_for_injection` (logging a warning on any hit), then `is_blocked_topic` (raising `ForbiddenError` if blocked), and finally `redact`. `sanitize_untrusted_document_text(raw_text)` redacts PII from document text and fences it via `wrap_as_untrusted(source="document")`, since documents are an adversarial, externally-supplied channel. `sanitize_tool_result(result_text)` does the same for tool output, fenced with `source="tool_result"`.

## How the pieces relate

`safety_pipeline.py` is the composition root — it's the only file here that imports from the other five validator/policy modules and the only one most of the rest of the app should call directly. The flow for user-facing chat input is: `input_validation` (structural checks) → `prompt_injection` (heuristic screen, logged but non-blocking) → `policy` (hard block on disallowed topics, raising) → `pii_redactor` (redact before the text ever reaches an LLM). Document and tool-result text skip straight to redaction plus `prompt_injection.wrap_as_untrusted`, since they're already-untrusted channels rather than something to validate structurally. `output_validator.py` sits on the opposite side of the LLM call: `validate_structured_output` is used when an agent needs a model's JSON-ish output coerced and checked against a schema, and `strip_unsafe_text` is the final check before any generated text is returned to a user. `policy.py`'s `SafetyAction` enum isn't invoked directly by the other files in this directory — it defines the vocabulary of decisions (allow/redact/block/escalate) that calling code (agents, review workflows) is expected to use when deciding what to do with the results these validators produce.
